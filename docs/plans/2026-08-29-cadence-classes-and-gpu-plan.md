## 1. Objective

Collect and store each metric at the cadence its physics needs, stop paying ~3.9 KB of permanent database growth per sample for a JSON blob nothing reads after an hour, and add a GPU collector that runs only where a GPU is detected — with zero subprocesses (ADR 0012's invariant, now extended to every collector). User-visible outcome: the live dashboard keeps its 1.5 s feel for CPU / RAM / swap / load / processes (and GPU where present); disk-space rows appear at a 60 s check cadence and are stored only when they change; the database's growth curve turns flat at the ladder's horizons instead of climbing ~640 MB per 72 h; `/api/snapshot` answers from memory. **Done =** every task's gate green outside the sandbox (`bun run check`), the migration `v1 → v2 → v3 → v4` proven on a copy of the live database, the 24 h growth measurement in §6 pasted, the deep dual-blind's fix round merged, `v0.6.0` released with audits.

## 2. Context & rationale

**Measured on the live box (0.3.1 binary, fresh v1 DB, 2026-08-29 15:3xZ, read-only):** `metric_samples` = 26,068 rows in 161.4 MB of pages, of which 68.8 MB is live `snapshot_json` (the 60-minute `snapshotJsonKeepMinutes` window — stripping keeps up) and **87.4 MB is unused space inside the table's pages (54.2 %)**: a stripped row leaves its mostly-empty 4 KB leaf page behind, ≈ 3.7 KB of slack per row, forever (until `VACUUM`). Typed payload per row ≈ 174 B. One snapshot's JSON is 28 KB: processes 18.5 KB (65.6 %, ten entries whose `command` carries the full argv, avg 558 chars stored), filesystems 8.3 KB (29.5 %, 27 mounts), everything else 1.25 KB. The daemon's CPU cost is not the problem (2.6 % lifetime average). `targetDatabaseBytes` enforces nothing (`lib.rs:1724-1728` computes a display percentage; no prune consults it) — the live DB sits at 122 % of it.

**What the code does today (v0.5.0):**
- One timer, one call: `spawn_collection_loop` (`agent/crates/tinytop-agent/src/writer.rs:856-867`) ticks every `poll_ms` (default 1500, `main.rs:28`; `DashboardSettings.poll_interval_ms` `tinytop-store/src/lib.rs:54`, validated 250..60,000 at `lib.rs:246`) and `collect_and_store` (`writer.rs:670-685`) calls `collector.collect()` once for the whole `SystemSnapshot` (`tinytop-collectors/src/lib.rs:19-21`; Linux impl `linux.rs:74-84` → `collect_sources` `:149-196` → `build_linux_snapshot_from_sources` `:93-147`; Windows/macOS = `common.rs::SysinfoCollector`). Filesystems are re-enumerated on every call (`linux.rs:169-171`, no cache); processes come from `sysinfo::System::processes()` sorted by CPU, **`take(10)` hard-coded** (`linux.rs:713-770`) — the setting `DashboardSettings.top_process_count` (`lib.rs:64`, default 8, validated 1..50 at `lib.rs:253`) is read by nothing.
- `insert_snapshot` (`lib.rs:922-1006`) always writes the full JSON into `metric_samples.snapshot_json`; typed detail rows go to `fs_samples` / `process_samples` (`migration.rs:157-189`) only when due per `retentionLadder.detailIntervalSec` (default 60, 15..3600) via `write_detail_rows_if_due` (`lib.rs:1238-1364`, gate on `history_state.lastDetailMs`, **no dedup against the previous row**), pruned at the L2 horizon only (`maintenance.rs:209` → `prune_detail_history` `lib.rs:1888-1902`).
- Readers of `snapshot_json`: `row_to_sample` (`lib.rs:2447-2459`) ← `latest_snapshot()` (`lib.rs:1370-1382`, backs **`/api/snapshot`**, handler `writer.rs:442-448`) and `read_history()` (`lib.rs:1386-1409`, backs **`/api/history`**, handler `writer.rs:456` via `read_history_with_backfill` `writer.rs:658-661`). Count-only: coverage `lib.rs:1669-1675` (`snapshotJsonSampleCount`/`snapshotJsonOldestMs`), `count_snapshot_json_older_than` (`lib.rs:1837-1842`, import dry-run `wouldDelete.snapshotJsonRows` `settings_transfer.rs:281-282`), `strip_snapshot_json` (`lib.rs:1864-1882`, `maintenance.rs:189-195`). `archive.rs`: none.
- Dashboard: live view polls `/api/snapshot` at `state.pollMs` (`app.js:2637`, `:3119`, `:3749`) and renders filesystems/processes from that payload (`app.js:2354-2356`); `/api/history` is fetched only for the raw windows `live`/`15m`/`1h` (`ladder-rules.js:47-50`, `app.js:3316-3410`) and the returned `.snapshot` objects are passed opaquely to the same render functions; longer windows use `/api/history/points` (`HistoryPoint` `lib.rs:538-550`: `cpuUsagePercent`, `memoryUsedPercent`, `swapUsedPercent`, `loadPercent`, `rootUsedPercent`). **The dashboard reads no `cpu.times.*` and no `pressure.*` field anywhere** (grep on `app.js` + `ladder-rules.js`); it reads `identity.{runtime,hostname,kernel,distro,uptimeSeconds}`, `cpu.cores`, `memory.totalBytes`, `swap.totalBytes`, `load.{runnable,totalThreads}` plus the charted percentages.
- The exporter (T11) already publishes every collected snapshot into `state.latest_snapshot` (a `tokio::sync::watch`, `writer.rs:678-680`) — the in-memory source `/api/snapshot` should have been reading all along.

**Decisions (each rejected alternative stated so the executor never reintroduces it):**
1. **Three cadence classes, owned by the collector, one writer tick unchanged.** `fast` = identity's uptime, cpu, memory, swap, load, pressure, processes (and GPU when detected) every tick; `slow` = filesystems every `retentionLadder.detailIntervalSec` (kept as the key name, redefined as the filesystem check interval; default 60); `static` = identity, read at start and re-read on the slow tick (hostname/kernel/distro can change only across a reboot or rename; cost is nil). Between slow ticks the collector serves the cached filesystem list and stamps `filesystemsCapturedAtMs` so the snapshot never claims a freshness it lacks. *Rejected:* separate tokio timers per class (three loops racing for one collector mutex and one store; the fold and the lock invariant were built around one tick) and per-metric intervals as settings (Michel's classes are the physics: CPU/RAM/swap/load/processes/GPU fast, disk slow; more knobs would be knobs nobody sets).
2. **History is typed; the per-sample JSON blob is dropped.** `metric_samples` loses `snapshot_json`; raw windows are reassembled from typed tables (`assemble_history_snapshot`). Fields the dashboard never reads and no history consumer needs are **not stored**: `cpu.times` (becomes `Option<CpuTimes>` on the type, `None` in history, `Some` live) and `pressure` (its `some`/`full` are already `Option`, `None` in history). This is an honest, documented drop, not a fake. *Rejected:* keeping the column nullable-but-unused (a fake), keeping a shorter JSON window (the slack is per row, the window length is irrelevant), storing PSI/cpu-times columns nobody reads (backlog: chart PSI first, then store it).
3. **Processes stay fast and get a dictionary.** `process_commands(command_id, command UNIQUE)` stores each distinct argv once; `process_samples_fast` holds one row per tick and rank (~45 B), pruned by `retentionLadder.processFastKeepHours` (default 24, 1..72); the existing 60-second `process_samples` rows (pruned at L2) continue unchanged as the minute tier and reference the same dictionary. `topProcessCount` is finally wired to the collector. *Rejected:* fast rows for the whole L1 window by default (~69 MB / 72 h — allowed by the setting, not the default), replacing the minute tier with a fold (a "top process" list has no meaningful average).
4. **Filesystems: check on the slow tick, store on change.** A row is written only when `used_bytes`, `available_bytes`, `size_bytes`, `inode_used` or `inode_total` differs from the last stored row for that mount (or the mount is new); reads carry the last row forward. *Rejected:* dedup by hash of the whole row (`used_percent` float noise would defeat it), storing every slow tick (27 mounts × 1,440/day × 30 days ≈ 117 MB for numbers that barely move).
5. **`/api/snapshot` answers from `state.latest_snapshot`** (the watch), not from the database. Before the first collection the route answers `503 {"error":"no snapshot yet"}`. *Rejected:* keeping the DB read (a JSON round-trip per dashboard poll for data the daemon already holds).
6. **GPU = detection-gated, per-OS backends, no subprocess, no vendor library.** Linux: DRM sysfs (`/sys/class/drm/card*/device/`) + `/proc/<pid>/fdinfo` DRM engine counters + the GPU node's hwmon; Windows: PDH (`Win32_System_Performance`) + DXGI (`Win32_Graphics_Dxgi`) through the `windows` crate already in the lock (0.62.2); macOS: IOKit `IOAccelerator` → `PerformanceStatistics` via a hand-declared framework FFI + the `core-foundation` crate already in the lock. No adapter → no sampler, no rows, no `gpus` section. NVIDIA's proprietary Linux driver exposes no utilization outside NVML (a vendor library) → identity only from `/proc/driver/nvidia/gpus/*/information`, `busyPercent: null`, documented. WSL2 has no DRM device (measured: `/sys/class/drm` holds only `version`; `/dev/dxg` only) → nothing is collected on WSL2, by rule. *Rejected:* `typeperf.exe` / `nvidia-smi` / `powermetrics` subprocesses (Michel 08-29: "I wouldn't want my daemon to run system calls for an exe file"; ADR 0012), NVML/ADL/AGS vendor SDKs, the Windows host's counters from inside WSL2. Temperatures, fans and power for GPUs belong to the (unstarted) sensors plan `docs/plans/2026-08-16-sensors-recording-plan.md` via hwmon; this plan collects busy % and memory only, and reads the GPU node's hwmon `temp1_input` opportunistically on Linux because it is the same directory (nullable).
7. **Rust-daemon-only (spec §13; ADR 0005/0009 pattern).** The Bun runtime keeps its loop and its JSON store untouched; the shared dashboard hides what Bun cannot serve, as the ladder group does. The sensors plan's older "every field in both runtimes" invariant is superseded by §13.
8. **Migrations are additive-or-drop, one per lane, chained `v1 → v2 → v3 → v4`**, each proven on a copy of the live database. Reclaiming the slack of an existing v1 file is the operator's `db vacuum` (never automatic — the pre-image/VACUUM law).

**Invariants the executor must keep:** the writer loop's status-lock invariant (`writer.rs:697-699` comment) — no `.await`, shutdown or store call under a `state.otel` guard; `DashboardSettings::from_document(document, Some(&previous))` is the ONLY decoder and an absent key keeps the persisted block; `put_settings_document` is the only write path for PUT and import (merge inside `BEGIN IMMEDIATE`); every validation message byte-identical between `otel_settings.rs`/`retention_ladder.rs` and `ladder-rules.js`; tests never touch `~/.local/share/tinytop`, `~/.config/systemd/user`, `:4274`, `:4317`, `:4318`; `serve_*` tests are the only port-bound tests; no `std::env::set_var`; the gate (`bun run check`) must leave `tinytop.service` `active`; lanes never commit — the orchestrator does.

**Storage model after this plan (expected, to be measured in §6):** `metric_samples` ≈ 174 B/row → ≈ 30 MB per 72 h at 1.5 s; `process_samples_fast` ≈ 10 × 45 B + index per tick → ≈ 35 MB per 24 h (default `processFastKeepHours` 24); `fs_samples` on-change → near zero between real changes; `gpu_samples` ≈ 30 B per adapter per tick → ≈ 1.7 MB per day per adapter; rollups unchanged. Steady state on this box ≈ 70–80 MB and flat.

## 4. Contingencies

- **If `ALTER TABLE … DROP COLUMN` fails** (`sqlite_version()` < 3.35, or the column is referenced by an index/trigger) → do NOT fall back to the copy-table dance silently: the migration must refuse with `schema migration requires SQLite ≥ 3.35.0 (linked: <version>)`; report. On this fleet the linked library is 3.51.x (`libsqlite3-sys` bundled), so this should not fire.
- **If the migration on the live-file copy takes > 60 s or the WAL grows past 1 GB** → stop, report the timing; the fix is batching the backfill `UPDATE` by `captured_at_ms` ranges, not skipping it.
- **If fdinfo files show engine names other than `drm-engine-<name>`** (e.g. `drm-cycles-*` only, on some i915 versions) → report the real lines and treat busy as `None` for that driver; never estimate from `drm-cycles` without the plan being amended.
- **If `gpu_busy_percent` exists but reads an error (trashcan's GCN 1 cards: `Operation not supported`)** → this is the expected fdinfo path, not a failure; cache the "unsupported" verdict per adapter and do not re-read the file every tick.
- **If PDH instance names on WizAI do not match the documented `pid_…_luid_…_engtype_…` shape** → paste five real instance names in the report; do not guess a regex.
- **If a test for `/api/history` assembly finds a dashboard-read field that cannot be reproduced from typed tables** → STOP: that field must gain a typed column in the same migration (report which); never leave it zero/empty.
- **If the collector's slow tick makes the first `/api/snapshot` wait** → the first call of every class is always due; if a test proves otherwise, fix the "first call" rule, do not add a warm-up sleep.
- **Default:** anything not covered here — STOP and reply `ESCALATE: <what, what you tried, where you stopped>`. Do not improvise around an undocumented obstacle.

## 5. Out of scope (do not build, even if it looks like an improvement)

Bun runtime changes of any kind (`src/`, `legacy/`); OTel GPU instruments (backlog); storing PSI or `cpu.times` in history (backlog after a chart exists); a PCI id → product-name table; NVML/ADL/AGS or any vendor library; any subprocess (`typeperf`, `nvidia-smi`, `powermetrics`, `sensors`, `df`); automatic `VACUUM`; enforcing `targetDatabaseBytes` (a separate decision — the disk check is the safety rule); temperatures/fans/power beyond the GPU node's own `temp1_input` (the sensors plan); changing `pollIntervalMs` semantics or default; refactors of the fold/prune code beyond the named prune additions; dependency bumps.
