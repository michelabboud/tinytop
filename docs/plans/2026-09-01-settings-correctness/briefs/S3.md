## The rule you are implementing

**The backend is authoritative.** It is the validator that can actually refuse a write, so the client mirrors it exactly — same rule firing, same words. A client that disagrees with the server means the message an operator sees depends on which validator ran first.

## F1 — the client must evaluate the rules in the backend's order

This is the part the plan missed, so read it carefully.

The backend (`agent/crates/tinytop-store/src/thermal_settings.rs:25-58`) checks the count once, then loops **per chip, in array order**, and returns on the first offending *element*: pattern (`:34-43`) → reserved (`:44-49`) → duplicate (`:50-54`).

The client (`ladder-rules.js:371-379`) checks each rule across the **whole array** in turn: count → `pattern.some` → `reserved.some` → duplicate.

These are not equivalent. For `["cpu_a", "cpu_a", "amdgpu"]` the backend reports **duplicate** (reached on the second element) and the client reports **reserved** (found by scanning the whole array for rule 3). Aligning only the strings would leave this in place.

**Restructure the client validator to walk the array once, per element, mirroring the backend**: count first, then for each chip in order — pattern, reserved, duplicate — returning the first failure. Keep returning an array of messages so the call sites are unchanged.

## F3 — M1: mirror the whole threshold band

`usableSensorThreshold` (`ladder-rules.js:127-129`) is `Number.isFinite(value) && value > 0`. ADR 0026 decision 4 defines the usable band as `0 < t <= 200 °C`, and the collector filters on it before serialising. The client mirrors only the lower half.

Add the upper bound. Consequence to preserve deliberately: an out-of-band ceiling makes `sensorBarPercent` return `null` (no bar) rather than scaling every reading against a nonsense maximum — which is what a `temp2_max` of `65261850` (observed on sheep's nvme) would otherwise do, rendering a permanently-empty bar with no explanation.

Unreachable from our own backend today; this is defence against any other producer of the same shape.

## F4 — M2: a reading with no chip must not head a group called `undefined`

`groupSensorsByChip` (`ladder-rules.js:143-152`) does `const chip = sensor?.chip` at `:147` with no guard and uses it directly as a `Map` key, so a reading without `chip` produces a group whose heading renders as the literal string `undefined`.

**Group such readings under `"unknown"`** — a real label. Do **not** silently drop them: losing a reading is worse than labelling it, and an operator seeing `unknown` can act on it. Treat any non-string or empty-string `chip` the same way. Unreachable from our own backend (chips with an unreadable `name` are skipped), so this is defensive only.
