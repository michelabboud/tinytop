**F1 — the registry, and `Instruments::new` built FROM it (ADR 0027 decision 4).** In `otel.rs`, add `#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize)] #[serde(rename_all = "camelCase")] pub struct MetricDescriptor { pub name: &'static str, pub unit: &'static str, pub family: &'static str, pub description: &'static str, pub semantic_convention: bool }` and `pub const METRIC_REGISTRY: [MetricDescriptor; 13] = [...]` carrying **exactly** the thirteen names and units read at `:263-318`, with `family` one of `"cpu" | "memory" | "swap" | "filesystem" | "pressure" | "load"` and `semantic_convention: true` for the ten `system.*` names, `false` for the three `tinytop.*` ones. `Instruments::new` then builds each gauge by looking its descriptor up in the registry (a small `fn descriptor(name: &str) -> &'static MetricDescriptor` that **panics with the missing name** — a registry that does not cover an instrument is a programming error, not a runtime condition). **The struct's thirteen typed fields stay** (they are how recording sites reach an instrument); only the name/unit strings move. Tests: the registry has 13 entries; every name is unique; every name matches `^[a-z][a-z0-9._]*$`; the ten/three semantic-convention split is asserted **by name**; and a test that fails loudly if `Instruments`'s field count and the registry length ever diverge (`METRIC_REGISTRY.len() == 13` beside a comment naming every field). Each unit string is asserted equal to what the pre-change code used — paste the before/after of all thirteen in your report.

**F2 — `disabledMetrics` on `OtelSettings` (ADR 0027 decisions 2 and 3).** Add `#[serde(default)] pub disabled_metrics: Vec<String>` to `OtelSettings`, `Default` → `Vec::new()`. `validate` gains: at most **64** entries (`"otel.disabledMetrics accepts at most 64 entries"`); each entry 1–128 characters matching `^[a-z][a-z0-9._]*$` (hand-rolled, in `valid_resource_attribute_key`'s style — **`otel.disabledMetrics entries must match ^[a-z][a-z0-9._]*$ and be at most 128 characters`**); **no duplicates**, rejected with a message naming the repeated value. **An entry that names no metric in `METRIC_REGISTRY` is VALID and is kept** — do NOT reject it, do NOT drop it, do NOT normalise it away (ADR 0027 decision 3: Michel runs one configuration across boxes on different releases, and a document from a newer tinytop must round-trip through an older one without losing his choices). *This crate cannot see `METRIC_REGISTRY` (it lives in `tinytop-agent`, which depends on the store, not the reverse) — that is fine and is the reason the rule is "accept anything well-formed": the store validates SHAPE, the agent decides MEANING.* Tests: the three rejections with their messages; **`unknown_metric_name_is_accepted_and_preserved`** (a name like `system.future.metric` survives validate and a settings round-trip byte-identically); the absent-key rule already covered by the existing `has_otel` test still passes; `default_settings_disable_no_metrics`.

**F3 — a disabled metric is never recorded (ADR 0027 decision 6).** In `collect_and_export`, compute the disabled set **once per export** as a `HashSet<&str>` from `settings.disabled_metrics` and skip the record call for any instrument whose registry name is in it. **Skip at record time — never build the payload and strip afterwards** (decision 6: that pays the collection cost for discarded data and can emit an empty metric some backends mishandle). A disabled metric must produce **no metric entry at all** in the OTLP request — not an empty one, not a zero data point. Tests, using the existing in-process receiver harness (`grep -n "serve_otel_receiver\|fn capture" otel.rs` for the shape — port 0, never `:4317`/`:4318`): with `disabled_metrics` empty, all thirteen names appear (assert the sorted name list verbatim); with `["system.filesystem.utilization", "system.filesystem.usage"]` disabled, exactly eleven appear and **neither disabled name is present anywhere in the request**; with an unknown name disabled, all thirteen still appear (it is inert — the proof of decision 3); with all thirteen disabled, the export still succeeds and reports no failure (an empty export is a valid state, not an error — assert the failure counter does not move).
