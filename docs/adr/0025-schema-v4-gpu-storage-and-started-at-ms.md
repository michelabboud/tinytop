# 0025 - Schema v4: GPU storage, `started_at_ms`, and the Linux GPU busy definition

## Status

Accepted (2026-08-30; Task 15 of plan `docs/plans/2026-08-29-cadence-classes-and-gpu-plan.md`, dispatched as lanes T15 + T15b, released as 0.5.4). Extends ADR 0022 (GPU sources) and ADR 0024 (decision 7 deferred `started_at` to v4). Amends the plan's Task 15 DDL (decision 2 below).

## Context

Task 15 ships the first GPU collector (Linux: DRM sysfs + `/proc/<pid>/fdinfo` + the GPU node's hwmon — ADR 0022) and schema v4. The plan fixed the sources and the trait shape but left four storage/semantics questions open, and two facts measured on 2026-08-30 change what an honest implementation can promise:

- **Measured on the fleet's GPU boxes (read-only, `fable@fabulous`, 00:3xZ):** trashcan (kernel 7.0) has two `amdgpu` adapters `0x1002:0x6810` at PCI slots `0000:02:00.0` / `0000:06:00.0`; `gpu_busy_percent` reads *Operation not supported*, `mem_info_vram_used/_total` = 6000640 / 2147483648, hwmon `temp1_input` 44000 / 45000, no `product_name`. sheep (kernel 6.8) has one `i915` adapter `0x8086:0x46d1` at `0000:00:02.0` with no busy file, no VRAM files and no hwmon. **Neither box had a single DRM client visible to the user the daemon runs as** (`/proc/<pid>/fd` of another uid is EACCES without `CAP_SYS_PTRACE`; the user is not in `render`/`video`, so it cannot even open a render node itself). This WSL2 box has `/sys/class/drm/version` only.
- **The kernel's contract** (`Documentation/gpu/drm-usage-stats.rst`): `drm-driver` mandatory; `drm-pdev`, `drm-client-id` optional; `drm-engine-<keystr>: <uint> ns` cumulative busy time, `drm-engine-capacity-<keystr>: <uint>` identical-engine count (default 1); utilisation is the delta between two reads; values "need not be strictly monotonic ... users should discard decreases"; the same client can be visible through several fds — deduplicate on `drm-client-id` (+ `drm-pdev`). Xe reports `drm-cycles-*`/`drm-total-cycles-*` instead of `drm-engine-*`.
- `SQLite strftime('%s', …)` parses the collector's `started_at` text (`2026-08-29T05:28:11Z`; also `+00:00` and fractional forms) and returns NULL for anything else — verified on 3.45 (this box) and identical on the bundled 3.51.
- T13 already provisioned `process_samples_fast.gpu_percent REAL` (written as NULL); the minute tier `process_samples` has no such column. T13 measured 66.7 B/row + 19.1 B/row index for the fast table with `started_at TEXT` against a ≤ 60 B target.

## Decision

1. **`started_at` becomes `started_at_ms INTEGER` in BOTH process tables, by REBUILD, in one transaction.** `process_samples_fast` (WITHOUT ROWID) and `process_samples` are each recreated as `<table>_v4` in the canonical fresh-file column order, copied with `CAST(strftime('%s', started_at) AS INTEGER) * 1000`, dropped and renamed; the three process indexes are recreated. A `started_at` that `strftime` cannot parse becomes NULL and is COUNTED (`startedAtUnparsed` in the `schemaMigrated` audit and the info line) — never a refusal: the field is display-only and the collector is its only writer. Guard: each rebuilt table's row count equals the source's, else the migration refuses and rolls back (the ADR 0023 in-flight guard, v4 edition). The JSON contract is unchanged: `startedAt` stays an RFC 3339 string, formatted at read (`2026-08-29T05:28:11Z` round-trips byte-identically because the collector's source is whole seconds). *Rejected:* `ALTER TABLE ... ADD COLUMN` + backfill + `DROP COLUMN` (appends columns at the end, so the migrated shape would differ from a fresh file and the T14-fix2 `table_info` equality proof could not hold); keeping TEXT (the ≤ 60 B/row target of ADR 0024 decision 7 is the point of v4); changing `startedAt` to a number on the wire (breaks the dashboard, the Bun runtime's shared dashboard and `docs/guides/API.md` for no reader's benefit).

2. **GPU adapters are interned with an integer surrogate key (amends the plan's `adapter_id TEXT PRIMARY KEY`).** `gpu_adapters (adapter_id INTEGER PRIMARY KEY, stable_id TEXT NOT NULL UNIQUE, vendor TEXT NOT NULL, name TEXT NOT NULL, driver TEXT NOT NULL, first_seen_ms INTEGER NOT NULL, last_seen_ms INTEGER NOT NULL)` and `gpu_samples (captured_at_ms INTEGER NOT NULL, adapter_id INTEGER NOT NULL REFERENCES gpu_adapters(adapter_id), busy_percent REAL, memory_used_bytes INTEGER, memory_total_bytes INTEGER, temperature_c REAL, PRIMARY KEY (captured_at_ms, adapter_id)) WITHOUT ROWID`. `stable_id` = `pci-<PCI_SLOT_NAME>` on Linux (`pci-0000:02:00.0`), else `card<N>`; Windows LUID and macOS registry id follow in Task 16. The store caches `stable_id → adapter_id` (primed at `connect`, like the identity cache) so a tick costs no lookup. **`last_seen_ms` is written at most once a minute per adapter** (a per-tick UPDATE would dirty a page every 1.5 s for a value nobody reads at that precision); the column's precision is "within a minute", documented. No secondary index on `gpu_samples`: the primary key serves the time-range reads and the prune; an adapter filter within a range scans a handful of rows per tick. *Rejected:* the TEXT key on every sample row (`pci-0000:02:00.0` is 16 bytes per adapter per tick inside the PK b-tree, against ≈ 30 B of payload — the same reason `process_commands` and `host_identity` intern); updating `last_seen_ms` every tick; deriving `last_seen_ms` from `MAX(captured_at_ms)` (lost once the L1 prune passes).

3. **GPU samples are raw-tier rows: written every fast tick, never deduplicated, pruned at the L1 horizon** with `metric_samples` (a new `prune_gpu_history` step beside "prune L1"; `MaintenanceReport.gpu_rows`). The import dry-run's `wouldDelete` gains `gpuSampleRows` (server-computed, same rule as `l1Rows`) so an L1 shrink never deletes GPU history silently; the dashboard shows the line only when non-zero and treats an absent field as 0 (a 0.5.3 daemon behind a 0.5.4 page). *Rejected:* on-change storage (busy changes every tick), a rollup tier for GPU (backlog — chart it first), a separate horizon setting.

4. **`gpu_percent REAL` is added to the minute tier (`process_samples`) in the same rebuild.** Replay older than `processFastKeepHours` reads the minute tier; without the column the GPU column would vanish at the 24 h boundary for no storage reason (10 rows/min). NULL where the collector has no value. *Rejected:* fast tier only.

5. **Busy % on Linux = Task Manager's definition on both fdinfo-driven OSes, one rule for the adapter and for a pid.** For every engine key: sum the client deltas, divide by `capacity × Δt`; the adapter's busy is the busiest engine, capped at 100. A pid's busy is the same computation over that pid's clients. Clients are deduplicated on (`drm-pdev`, `drm-client-id`) — a client visible through two fds or two pids counts once (for the first pid seen). A decreasing counter contributes 0 for that interval; a client first seen this tick has no delta; the first tick after start or re-detect reports `busyPercent: null`. Δt is the monotonic interval between two scans, never wall-clock. **`gpu_busy_percent` is preferred when it reads a number; a read or parse error is cached per adapter as "unsupported" until the next re-detect (the slow tick) — never re-read every tick.** Xe's `drm-cycles-*` form is reported as `null` with a log line naming the driver; supporting it is backlog (no Xe hardware in the fleet to verify against). **The scan covers only pids whose `/proc/<pid>/fd` is readable by the daemon's uid; on a multi-user box the fdinfo-derived adapter busy is therefore a lower bound and per-process GPU % covers the daemon user's processes (plus everything, when the daemon runs as root).** This is documented in README/API, not hidden. *Rejected:* summing engines per client ("render + copy = 200 %"); the sum of per-engine utilisations (i915's `intel_gpu_top` shows engines separately — TinyTop's panel has one number); wall-clock Δt; estimating from `drm-cycles` without hardware to verify; requiring `CAP_SYS_PTRACE` or a root daemon.

6. **Task 15 is two lanes with disjoint files, one tag.** `briefs/T15.md` (types + collectors + store + agent + the store/API docs, `ari-sol-deep`, branch `tinytop/phase5-t15-gpu-linux`) and `briefs/T15b.md` (dashboard assets + Bun tests + `GUIDE.md`, `ari-sol`, branch `tinytop/phase5-t15b-gpu-dashboard`), both from `main`, merged store first, released as 0.5.4 — the T14/T14b shape. The dashboard's GPU panel is a `section.panel` placed after the four-gauge overview grid (the grid's `repeat(4, …)` layout stays; a fifth gauge would wrap onto its own row), hidden when `snapshot.gpus` is empty or absent (the Bun runtime never sends it); the process table gains a `GPU` column shown only when a row carries a value.

7. **Fixtures are written from the kernel document and the measured sysfs trees; real fdinfo lines are validated at acceptance, not in the sandbox.** The lane cannot see a DRM device (WSL2) and the orchestrator could not capture a real fdinfo dump without a group grant. The plan's `[JUDGMENT-HEAVY]` rule stands: if the kernel's real lines on trashcan (amdgpu 7.0) or sheep (i915 6.8) differ from the fixtures in a way the parser rejects, that is a fix lane, not a parser guess. The acceptance runs the ignored `live_gpu_scan_cost_on_this_host` instrument on both boxes and pastes `GpuScanStats` (duration, pids scanned, pids denied, clients) — rule 8: the scan's cost is measured, not asserted.

## Alternatives rejected (summary)

- Vendor libraries, subprocesses, reading the Windows host from WSL2 — ADR 0022.
- A PCI id → product-name table — ADR 0022; the name is `product_name` when the FRU exposes it (server cards), else the `vendor:device` id pair (`0x1002:0x6810`).
- OTel GPU instruments, a GPU rollup tier, a GPU retention setting — backlog.
- Any change to the Bun runtime.

## Consequences

- v4 rebuilds two process tables: on a 24 h default window that is ≤ ~600 k fast rows + ~430 k minute rows — seconds, measured at the T15 gate on a fresh copy of the live file (plan §4: > 60 s → batch the copy, never skip).
- Expected fast-row cost ≈ 52 B/row (the 14-byte text becomes a 6-byte varint); the target ≤ 60 B/row is measured with `dbstat` at the gate.
- `gpu_samples` ≈ 30 B/adapter/tick ≈ 1.7 MB/day/adapter, flat at the L1 horizon; zero rows and an empty `gpu_adapters` on a box without a GPU (WSL2 proves it).
- `/api/history/gpus` (additive), `gpus[]` in `/api/snapshot` and assembled `/api/history` samples (absent when empty), `processes[].gpuPercent` (absent when unknown), `db stats` gains `gpuAdapterCount` / `gpuSampleCount`, the dry-run gains `wouldDelete.gpuSampleRows`.
- The Windows/macOS GPU backends remain explicit "not implemented" returns (Task 16); the cross-target per-crate checks stay green.
